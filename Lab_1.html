OBJECTIVE

By exploiting a vulnerability caused by a buffer overflow on a 64-bit architecture, obtain a reverse shell that allows taking remote control of the target system.

Memory architecture in x86-64

To gain an in-depth understanding of the exploited vulnerability, it is necessary to understand how the operating system organizes RAM during the execution of a process. On 64-bit architectures (x86-64), Linux assigns a private virtual memory space for each process, structured into the following segments:

SegmentFunctionTypical addresses
.textMachine code of the program (instructions)Low (0x400000)
.dataInitialized global variablesFollows .text
.bssUninitialized global variablesFollows .data
HeapDynamic memory (malloc, new)Grows upward (↗)
StackLocal variables, function callsGrows downward (↙) from high addresses

Memory layout sketch of an x86-64 process

Zoom into the stack segment

When a function is called, the system reserves a frame (stack frame) on the stack that contains:

  1. Function arguments (if they don't fit in registers).
  2. The return address (saved RIP): instruction to which the program must return at the end of the function.
  3. The previous value of the $rbp register (base pointer), to restore the context of the calling function.
  4. The function's local variables (in our case, the buffer[]).

Detailed analysis:
  • Buffer start address: 0x7fffffffcb20 (where the 'A's and then 'B's are stored).
  • Address where the previous $rbp is saved: 0x7fffffffcd30 (value: 0x00007fffffffe2c0).
  • Address where the return $rip is saved: 0x7fffffffcd38 (original value: 0x00005555555557bf, which points to the return address within the code in main).
The attacker's goal is to overwrite the address at 0x7fffffffcd38 with a controlled address (for example, the buffer itself 0x7fffffffcb20), so that when the function executes ret, the program jumps to the injected shellcode.

Offset calculation

The difference between the address of $rbp (0x7fffffffcd40) and the start of the buffer (0x7fffffffcab0) is:

0x7fffffffcd30 - 0x7fffffffcb20 = 0x210 = 528 bytes

Since the $rip is saved immediately after the $rbp (8 bytes higher), the total offset to reach and overwrite the return address is:

528 bytes + 8 bytes = 536 bytes

This means that the first 536 bytes of the message sent by the client will fill the buffer and then write exactly over the saved $rip. The following 8 bytes will be the new return address (in our case, the buffer where the shellcode resides).

Note that the address we will jump to will be 0x00007fffffffcbe4 (180 bytes after the buffer start), which contains NOP instructions and will continue with the payload's execution.
